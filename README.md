# 尼康 L 固件（失真控制数据 / “镜头校准文件”）研究笔记

日期：2026-11-11　范围：**只读静态分析**。对象是尼康公开下载的 Distortion Control Data（相机内显示为
`L` / `LD`）数据文件，以及手头已有的机身固件镜像。没有向任何相机写入，也没有生成可刷写的固件。

## 0. 结论速览

- 下载页上的“镜头校准文件”就是尼康英文页的 **Distortion Control Data**（中文页“失真控制数据”），
  当前版本 **2.018**，解包后的实际文件是 **`NKLD0218.BIN`**（39,588 字节）。
- 容器结构已完整解出并用 2.017 / 2.018 两版交叉验证：
  32 字节大端头 + `N` 条 128 字节记录（20 字节头 + 27 个 32 位词）+ 尾部（2 个 CRC16 + `M` 个
  52 字节条目 + 0xCD 填充）。
- 记录的 27 个系数词**不是明文**：高 16 位按低 16 位的符号在 `M`/`~M` 之间翻转（98.36% 吻合），
  是“32 位 XOR 密钥作用在符号扩展的 16 位系数上”的特征。密钥低半已用平滑性先验恢复，但每列仍有
  4 重符号歧义，尚未定论。
- 在 D750 主固件里定位到相机端的文件名模式 `NKLD????.BIN`、升级文件类型表，以及一个按
  “32 字节偏移 + u16 大端记录数 + 0x80 步长”遍历记录的查找函数，与文件布局完全吻合。
- 重打包原型可以改字节并修好两个 CRC16；容器没有签名。

## 2. 容器格式（全部大端）

```
偏移      类型   说明
0x0000    u16    数据区偏移 = 0x0020
0x0002    u16    0
0x0004    u16    版本：0x0211 = 2.017，0x0212 = 2.018（低字节是十进制数的十六进制写法）
0x0006    u16    记录条数 N（2.017: 301，2.018: 307）
0x0008    u32    魔数 0x87C7CAAC（文件里就是字节 87 C7 CA AC）
0x000C    u32    2 + N*128
0x0010    u32    0
0x0014    u32    0
0x0018    u32    0
0x001C    u16    0
0x001E    u16    0x20 + N*128 + 4
0x0020    N × 128 字节记录
```

尾部（紧接记录区）：

```
尾部偏移   类型   说明
+0x00      u16    CRC16（poly 0x1021, init 0），覆盖“头部 + 全部记录”
+0x02      u16    0
+0x04      u32    魔数 0xF8E7C8A6
+0x08      u32    0
+0x0C      u32    0x18 + M*52（条目区结束偏移；2.017: 180，2.018: 232）
+0x10      u16    M = 条目数（2.017: 3，2.018: 4）
+0x12      u16    0
+0x14      u16    52（条目长度）
+0x16      u16    0
+0x18      M × 52 字节条目
+0x18+M*52 u16    收尾 CRC16：存储值 = crc16(文件开头 .. 本字段之前)，不含末尾 0xCD 填充
+...       u16    0
之后       0xCD 填充到文件末尾（两版都是 24 字节）
```

实测：

```
2.017: 数据 CRC 6358 ✓   收尾 CRC 968E ✓   (尾部 208 B，3×52)
2.018: 数据 CRC 5920 ✓   收尾 CRC EAD2 ✓   (尾部 260 B，4×52)
```

校验算法是尼康固件里一贯的 CRC16/CCITT：poly `0x1021`、初值 0、无终值异或
（`binascii.crc_hqx(data, 0)`）。

> **CRC 残差**：`crc16(A || crc16(A)) == 0`，所以收尾 CRC 实际只校验数据 CRC 之后的内容。
> 改一条记录只会改变数据 CRC；改尾部条目才会改变收尾 CRC（实测 5920→4078 / EAD2 不变，
> 以及 5920 不变 / EAD2→2225）。

## 3. 128 字节记录

按 D750 查找函数的拷贝循环逐字段核对（VA `0x9004DB5C`，大端→小端逐字节倒序）：

```
+0x00  u16   类型标签：0x3433 / 0xF473 / 0xB4B3 / 0x74F3（按记录序号 mod 4 轮转）
+0x02  u16   查找键 1
+0x04  u16   查找键 2
+0x06  u8    拷贝进运行时结构
+0x07  u8    查找键 3
+0x08  u8    查找键 4
+0x09  u8    未使用
+0x0A  u32   word A（大端，整体倒序后拷入）
+0x0E  u32   word B
+0x12  u16   half C
+0x14  27 × u32 系数（大端，每 4 字节倒序后拷入；0x14 + 108 = 0x80）
```

同一相位的记录大量字节相同，键字段平滑递减（0x116A→0x1169→0x1166…），说明记录按镜头顺序存放。

## 4. 系数区的 XOR 混淆与密钥恢复

对 27 个系数词逐位置统计：每个 (相位, 词序号) 的高 16 位只有 2~4 种取值，且几乎总是 `M` 与 `~M`
成对；把它与低 16 位的符号位对齐后，**98.36%（8153/8289）**满足“低 16 位为负 → 高 16 位取 `~M`”。
2.017 同样成立（98.33%）。这正是

```
cipher = plaintext ^ key,   plaintext_high = 0x0000 / 0xFFFF（16 位符号扩展）
```

的特征，即明文是 16 位有符号系数，文件用一个按位置固定的 32 位密钥 XOR。

### 4.1 密钥低半

同一镜头的记录相邻，所以正确密钥应让解码后的系数序列最平滑。对每个位置在 65536 个候选里搜索
“相邻同相记录差之和最小”的密钥（`tools/recover_key.py`），结果：

| 指标 | 值 | 随机基线 |
| --- | --- | --- |
| 27 值中位数 \|v\| | 157 | ~16384 |
| \|v\| < 5000 | 92.3% | ~15% |
| 恰好为 0 | 7.7% | ~0.002% |
| 9 组三联 (c0,c1,c2)… 满足 \|a\|≥\|b\|≥\|c\| | 38.4% | 15.8% |

分相位中位数 143 / 256 / 104 / 156。零值集中在特定列（c24 41%、c14 28%、c16 27%），像“空槽”；
三联单调性高于随机，支持“9 个焦距位置 × 3 个系数”的布局。第 1 条记录（相位 1 首条）中位数
~10411，异常，可能是默认/哨兵记录。

**4 重歧义**：每个位置上 `v`、`~v`、`v^0x8000`、`~v^0x8000` 解码后同样平滑（只差取反/半程平移），
单凭文件无法确定符号方向。目前保留 `mean|v|` 最小的代表，因此**幅值可信、每列符号方向待定**。

试着用“9 组三联、每组 (k1,k2,k3) 应随焦距平滑”来定符号：对 27 列做坐标下降翻转（最小化组内
一阶差分之和），只把粗糙度降到 73%，k1 序列（如记录 4：-1369,-670,0,667,-1,143,-586,-314,0）
仍不平滑。这说明仅靠“9×3 + 逐列符号”还不足以解释数据——布局或符号模型仍有缺失，需要外部真值。

### 4.2 密钥表搜索（负结果）

在 `b1010_115a.bin`、`a1010_011100.bin`、`eg1510_012100.bi`、`b860_102.bin` 里查找过这把密钥：

- 108 个 u16 的序列（允许逐位取反），u16/u32 步长、所有字节对齐、大小端各一遍；
- 密钥低字节/高字节流（含取反）的子串搜索。

全部未命中（最长连续匹配 1~2 个值，与随机无异）。密钥不是以明文表形式存在这些镜像里，
可能在 boot ROM/OTP、独立 L 数据分区，或由运行时算法生成。

## 5. 版本演进：2.017 → 2.018

- 记录数 301 → 307（+6 条 = 768 字节）；尾部条目 3 → 4（+1 条 = 52 字节）；文件增大 820 字节。
- 头部/记录区前缀逐字节相同，新增数据在尾部附近，是纯追加式演进。
- 头部变化：版本 `0x0211→0x0212`、条数 `0x012D→0x0133`、长度 `0x9682→0x9982` /
  `0x96A4→0x99A4`，两个 CRC 随之改变。
- 尾部 `+0x0C` 180 → 232，`+0x10` 3 → 4，`+0x14` 保持 52。

## 6. 机身固件侧证据（D750 / D780 / D3300）

样本：`b1010_115a.bin`（D750 主，基址 `0x90020000`）、`eg1510_012100.bi`（D780 主，基址
`0x10020000`）、`b860_102.bin`（D3300 主，带大量调试符号）。

1. **文件名模式表**：D750 在文件偏移 `0x126B44E`（VA `0x9128B44E`）有 `NKLD????.BIN`，前后是
   `_WT7????.BIN`、`WR1?????.BIN`、`D750_???.BIN` 等模式，位于 VA `0x90E7DF28` 起的 12 字节表
   `{u32 id, char* pattern, u32 handler}`，NKLD 对应 id 6。相机靠 **`NKLD` + 4 位版本号 + `.BIN`**
   识别卡上的文件。
2. **记录遍历/查找函数**：VA `0x9004D924`（Thumb）。
   - 用 `u16 BE(header+0)` 作记录偏移（0x20），`u16 BE(header+6)` 作条数；
   - 从 `base+0x20` 起按 **0x80** 步长遍历，比较记录 `+2`、`+4` 的 u16 和 `+7`、`+8` 的字节；
   - 命中后把记录 `+0..+0x13` 和 `+0x14..+0x7F` 的 27 个大端字逐字节倒序拷进 0x84 字节运行时结构；
   - 校验头部 `+8` 魔数 `0x87C7CAAC`、`+4` 版本字节 `== 2`。
   - 3 个调用点：VA `0x9004E5FC`、`0x9017E7F2`、`0x9018113A`；前者用 `rec+6`、`rec+0x12`
     做移位/查表（EXIF 镜头信息路径）。
3. **插值/应用代码**：VA `0x9004DC04` 是二维表插值（u16 计数/步长、int16 边界、两个数组指针，
   定点乘加 + 四舍五入），与“按焦距/像高插值”一致。
4. **D780 内嵌描述符**：文件偏移 `0x1742FB8` 有静态数据，包含 `0x9682/0x96A4`（2.017 长度）、
   尾部魔数、`0xE8/4/0x34`（与 2.018 的 232/4/52 一致）和 `0xB4/2/0x34`。说明固件按
   “版本 + 长度 + 条目数”校验，但 `0xB4/2` 与 2.017 的 `180/3` 不完全对应，待更多样本。
5. **D3300 符号串**：1105 条“长度前缀 + 名字”（`25CPTPCGetLensDataFlashRead`、
   `26CPTPCSetLensDataFlashWrite`、`19CAINFLensDistortion`、`24CIEFUDistortionParameter` 等）。
   每条只被引用一次，引用处是 `{name_ptr, owner_ptr, type_ptr}`（Get/Set LensDataFlash 共享
   owner `0x91502514`），是**类成员/接口元数据**，不是函数地址表。

## 7. 重打包原型与校验路径

工具：`tools/nkld_repack.py`

```powershell
# 改记录里的 4 字节系数，并自动修两个 CRC
python tools/nkld_repack.py patch NKLD0218.BIN out.bin --record 0 --offset 0x14 --hex DEADBEEF

# 改任意文件偏移（例如尾部 52 字节条目）
python tools/nkld_repack.py patch-raw NKLD0218.BIN out2.bin --offset 0x99BB --hex 00

# 自检：翻一个字节 + 修 CRC + 重新解析
python tools/nkld_repack.py selftest NKLD0218.BIN
```

| 操作 | 数据 CRC | 收尾 CRC | 解析校验 |
| --- | --- | --- | --- |
| 原始 2.018 | 5920 | EAD2 | OK |
| 改记录 0 系数 | 5920 → 6DC1 | EAD2（不变） | OK |
| 改尾部条目 1 字节 | 5920（不变） | EAD2 → 2225 | OK |

容器没有签名，只有 CRC16；改记录只需修数据 CRC。注意 `patch` 改的是**密文**，要让系数变成想要的
值，得先确定 XOR 密钥的符号方向（见 4.1）。

静态校验：查找函数只依赖魔数/版本/偏移/条数，不改这些字段即可保持结构合法；固件里存在
`header crc mismatch`、`CRC error` 字符串和 CRC16/CCITT 表（文件偏移 `0x12ACD7C`），但“卡上
NKLD 写 flash 前是否调用”尚未定位。

## 8. 尚未解决的问题

1. **每列符号方向**：4 重歧义未解，需要相机端解混淆代码或一台相机 flash 里的明文 L 区。
2. **记录字段语义**：`+2/+4` 查找键和 `+7/+8` 字节对应镜头信息的哪些字段；`word A/B`、`half C`
   的用途；27 个 16 位系数是否就是“9 焦距位置 × (k1,k2,k3)”。
3. **尾部 52 字节条目**：每版本 3→4 条，内容高熵，作用不明。
4. **flash 布局**：卡上文件是原样写入 flash，还是升级时先解混淆再写；写前 CRC 校验调用点未定位。

## 12. 新的切口（D90 → D780 通用）

同一份 L 数据从 D90（2008）用到 D780（2020），说明解混淆/解析逻辑在所有机身里都存在，包括最老、
最小的 D90。据此补了一轮探测，详见 **[docs/leads.md](docs/leads.md)**，要点：

- 尾部 52 字节条目是**按代追加**的：2.017 的 3 条在 2.018 里逐字节保留，只新增第 4 条；
- D90 固件是半明文，`NKLD????.BIN`（`0x21305E`）、魔数 `0x87C7CAAC`（`0x1ACFA4`）和文件类型
  偏移表（`0x213000`）都能直接看到；已在 WSL 里构建 FR30/FR-V 的 objdump，但 D90 代码对两者都
  只有 10%~25% 可识别率（见 docs/leads.md 第 6 节），需要 FR60 级解码器或 flash dump；
- D7200 解密镜像同样有 `NKLD` 入口，但密钥表扫描仍为负；
- 密钥在 D90/D7200/D750/D780/D3300 六个镜像里都不以明文表存在；
- 值得继续的切口：FR 反汇编 D90、用 WMA_ 容器做已知明文对、老版本 L 数据（2.000/2.013）、
  PTP 读 L flash（`CPTPCGetLensDataFlashRead`）。
